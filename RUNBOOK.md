# Daily update procedure

The connected Codex automation is the scheduler. No brokerage credentials, API tokens, private account responses, balances, positions, or complete watchlist exports belong in this public repository.

1. Read current `main` and this procedure. Fetch the current IBKR watchlists named US AI, Korean AI, Japan AI, Taiwan AI, and Euro AI. Exclude China AI and every other list. Keep raw brokerage responses only in private local working files. Resolve instrument identities when necessary; deduplicate multiple listings of one company while retaining its source watchlist grouping.
2. Use a rolling seven-day window in America/Los_Angeles on every run: today through today plus six calendar days, inclusive (00:00 today through 00:00 on day seven exclusive). Set `window_type: rolling_7_days`, `window_start`, and `window_end`; the renderer validates exactly seven dates. Sunday uses the same rule and still delivers a concise rolling preview in the originating chat. Screen the entire selected scope for the window, including adjacent overseas local dates that can shift into Pacific time. Never wait for a Monday or calendar-week boundary. Preserve the historical `weeks/` files unchanged; save new rolling snapshots as `snapshots/YYYY-MM-DD.md` using the Pacific run date.
3. Screen reputable earnings calendars, then prioritize current company IR announcements and exchange disclosures. Use local-language sources for overseas issuers. Distinguish confirmed announcements, calendar estimates, conflicts, and unknowns. A missing source or an unresolved identity is a coverage limit, not proof of no earnings.
4. Update `data/calendar.json` with event records and direct source URLs. Record exact timestamps with their UTC offsets. Keep session-only releases as `session`, `date`, and `exchange_timezone`; do not invent a timestamp. A call time cannot establish the release time. Keep unknown timing as an explicit note. For a source-local date with no time, use `local_date` and an IANA `timezone`; show the possible Pacific date range. Preserve explicit timing bounds as `before` or `not_before`, not exact `at` timestamps. Preserve the source-local date/time in `source_timing` when available.
5. Convert source dates and times using America/Los_Angeles. Use the correct offset on the event date, including U.S./European daylight saving differences and prior-day shifts from Asia. When the source gives only a local date without a time, do not silently assign a single Pacific date. Explain any timezone-label conflict and prefer an explicit UTC offset or cross-zone equivalent provided by the company.
6. Keep five regional sections using watchlist grouping. Preserve all source labels in `watchlists`; show a company once and annotate the extra groups when multiple selected lists contain it. For a company on a selected native-region list and also an ADR/foreign-listing alias, prefer its native-region watchlist section; an issuer with only US AI membership stays in United States regardless of headquarters. Put tentative candidates in `unresolved`. Include a company whenever any release, call or quarterly presentation component overlaps the rolling window. Date-only timing intervals may overlap a boundary and must stay explicitly uncertain. Hide rows whose components are entirely before the window from the current tables while retaining data/history. If an event moves beyond the rolling window, retain its new verified date under confirmed later dates and record a concise correction in `changes`. Later dates are not an exhaustive next-week preview.
7. Set the Pacific verification timestamp honestly after research. If part of the review fails, retain prior source-checked data and label the affected region as partially verified; do not claim a full refresh. Never overwrite good data with an empty result caused by a service failure. Git history records the actual publication time.
8. Run `python3 scripts/render_calendar.py`. Check weekdays, Pacific conversions, duplicate companies, scope, links, and any meaningful source conflicts. Inspect the rendered Markdown. Keep only calendar-related public information in every committed file.
9. Publish the JSON, README, current rolling snapshot, and any intentional procedure changes in one commit. Use a non-forced expected-head update on `main`; on a conflict, read the new head and reconcile without overwriting unrelated changes. Fetch the published README and JSON to verify the commit before claiming success.
10. If inputs and table are unchanged apart from the advancing window, a daily verification timestamp update is allowed. Report access failures and required user action in the originating chat. Keep routine daily runs quiet unless dates/times materially change; deliver the Sunday rolling-seven-day preview even when there are no earnings.

The standard-library renderer is deterministic and requires Python 3.9+ with timezone data. It performs no account access or network research itself. The connected automation performs the research and publication.
