# Daily update procedure

The connected Codex automation is the scheduler. No brokerage credentials, API tokens, private account responses, balances, positions, or complete watchlist exports belong in this public repository.

1. Read current `main` and this procedure. Fetch the current IBKR watchlists named US AI, Korean AI, Japan AI, Taiwan AI, and Euro AI. Exclude China AI and every other list. Keep raw brokerage responses only in private local working files. Resolve instrument identities when necessary; deduplicate multiple listings of one company while retaining its source watchlist grouping.
2. Use the current Monday–Sunday as the reporting week in America/Los_Angeles. On Sunday, advance to the coming Monday–Sunday and deliver the weekly preview in the originating chat. Preserve existing weekly snapshots. Explicitly inspect the target week's earnings across all five selected lists, rather than only rechecking previously known events.
3. Screen reputable earnings calendars, then prioritize current company IR announcements and exchange disclosures. Use local-language sources for overseas issuers. Distinguish confirmed announcements, calendar estimates, conflicts, and unknowns. A missing source or an unresolved identity is a coverage limit, not proof of no earnings.
4. Update `data/calendar.json` with event records and direct source URLs. Record exact timestamps with their UTC offsets. Keep session-only releases as `session`, `date`, and `exchange_timezone`; do not invent a timestamp. A call time cannot establish the release time. Keep unknown timing as an explicit note. Preserve the source-local date/time in `source_timing` when available.
5. Convert source dates and times using America/Los_Angeles. Use the correct offset on the event date, including U.S./European daylight saving differences and prior-day shifts from Asia. When the source gives only a local date without a time, do not silently assign a single Pacific date. Explain any timezone-label conflict and prefer an explicit UTC offset or cross-zone equivalent provided by the company.
6. Keep five regional sections using watchlist grouping, not company headquarters. Put tentative candidates in `unresolved`. If an event moves beyond the reporting week, retain its new verified date under confirmed later dates and record a concise correction in `changes`. Later dates are not an exhaustive next-week preview.
7. Update the Pacific publication timestamp only after research succeeds. If part of the review fails, retain prior source-checked data and label the affected region as partially verified; do not claim a full refresh. Never overwrite good data with an empty result caused by a service failure.
8. Run `python3 scripts/render_calendar.py`. Check weekdays, Pacific conversions, duplicate companies, scope, links, and any meaningful source conflicts. Inspect the rendered Markdown. Keep only calendar-related public information in every committed file.
9. Publish the JSON, README, current weekly snapshot, and any intentional procedure changes in one commit. Use a non-forced expected-head update on `main`; on a conflict, read the new head and reconcile without overwriting unrelated changes. Fetch the published README and JSON to verify the commit before claiming success.
10. If inputs and table are unchanged, a daily verification timestamp update is allowed. Report access failures and required user action in the originating chat. Keep routine daily runs quiet unless dates/times materially change; deliver the Sunday preview even when there are no earnings.

The standard-library renderer is deterministic and requires Python 3.9+ with timezone data. It performs no account access or network research itself. The connected automation performs the research and publication.
